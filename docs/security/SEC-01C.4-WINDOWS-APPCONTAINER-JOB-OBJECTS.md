## 1. Executive Summary & Threat Model

Sarthi's mission is to execute untrusted code generated by AI coding agents—including unit tests, linters, dynamic scripts, and test runners—with guaranteed kernel-enforced containment. Application-level path validation (e.g. `PathGuard`) and environment sanitization provide defense-in-depth, but cannot stop an adversarial subprocess executing native Windows system calls (`NtCreateFile`, `WSAStartup`, `CreateProcessW`).

On Windows, standard user subprocesses inherit the developer's complete security token (`Medium` or `High` integrity), allowing unrestricted read/write access to `%USERPROFILE%/.ssh`, `%APPDATA%`, cloud credentials, browser keystores, and local network loopback interfaces (`127.0.0.1:5432`, `127.0.0.1:6379`).

**SEC-01C.4 introduces a genuine Windows OS-level sandbox backend** that combines two foundational Windows NT security primitives:
1. **Windows AppContainer (LowBox isolation):** Enforces an un-bypassable token-based security boundary. The kernel Security Reference Monitor (SRM) checks every securable object against the AppContainer Package SID (`S-1-15-2-...`), denying access to any host resource unless explicitly granted via an Access Control Entry (ACE).
2. **Windows Job Objects:** Enforces hard resource ceilings (commit charge memory caps, process tree limits) and guarantees atomic, zero-orphan process tree termination upon exit or timeout (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`).

## 2. Windows Security Primitives Audit

### 2.1 Standard AppContainer vs. Less-Privileged AppContainer (LPAC)
An in-depth security evaluation was conducted comparing Standard AppContainers and Less-Privileged AppContainers (LPAC):
- **Standard AppContainer:** The token possesses the `ALL APPLICATION PACKAGES` well-known SID (`S-1-15-2-1`). This grants read access to common OS components and system binaries (e.g., `C:\Windows\System32`), while strictly denying access to user directories, `%USERPROFILE%`, registry SAM/SECURITY hives, and arbitrary host drives.
- **LPAC (Less-Privileged AppContainer):** LPAC strips even `ALL APPLICATION PACKAGES`, restricting the token to `ALL RESTRICTED APPLICATION PACKAGES` (`S-1-15-2-2`). While providing extreme containment, standard runtime execution (such as loading C++ runtime DLLs, Python standard library modules, or core Win32 subsystems) requires explicit OS ACL granting that is fragile across diverse developer Windows versions.
- **Decision:** Sarthi implements **Standard AppContainer with zero granted capabilities**, paired with strict handle filtering (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) and explicit additive DACL scoping. This guarantees impervious containment of developer secrets and host networks without breaking the Python interpreter or native C extensions.

### 2.2 Network Isolation via Windows Filtering Platform (WFP)
In the Windows NT architecture, network isolation for AppContainers is not handled via firewall rules; it is enforced directly by the Windows Filtering Platform (WFP) within the network stack (`tcpip.sys`):
- Standard UWP/AppContainer apps declare capabilities such as `internetClient`, `privateNetworkClientServer`, or `loopbackExempt`.
- `WindowsAppContainerBackend` initializes AppContainers with **`CapabilityCount = 0`**.
- Under a zero-capability LowBox token, WFP unconditionally rejects all socket operations:
  - WAN egress attempts (`8.8.8.8:53`, `google.com:443`) return `WinError 10013 (WSAEACCES)`.
  - Loopback connections (`127.0.0.1`, `::1`) are dropped by default LowBox loopback isolation.
  - Raw socket creation and ICMP pings fail immediately with `Unable to contact IP driver. General failure.`

### 2.3 Filesystem Access Control & Additive DACL Model
To prevent privilege escalation or credential leakage:
- Pre-existing ACLs on the host filesystem are never modified or weakened.
- For each execution, Sarthi creates an ephemeral staged workspace directory and extracts the derived AppContainer SID (`S-1-15-2-X-Y-Z...`).
- Additive DACLs are injected solely on:
  1. **The staged workspace:** Granted `(OI)(CI)(F)` (full control within the ephemeral stage).
  2. **The host Python runtime & virtualenv:** Granted `(OI)(CI)RX` (read and execute only).
- When the subprocess attempts to traverse directory junctions, reparse points, or relative parent paths (`..\..\`), the kernel SRM re-evaluates the target object's DACL against the LowBox token and rejects access (`STATUS_ACCESS_DENIED`).

## 3. Job Object Resource Enforcement

Windows Job Objects provide hard resource containment that survives subprocess fork bombs and runaway allocations.

### 3.1 Resource Ceilings
Configured via `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`:
- **`JOB_OBJECT_LIMIT_PROCESS_MEMORY` & `JOB_OBJECT_LIMIT_JOB_MEMORY`:** Hard commit charge limit (default 512 MB). If a process attempts to allocate beyond the quota, `VirtualAlloc` fails with `ERROR_COMMITMENT_LIMIT_EXCEEDED` (or Python raises `MemoryError`).
- **`JOB_OBJECT_LIMIT_ACTIVE_PROCESS`:** Hard process concurrency limit (default 32 processes). Prevents fork bombs from exhausting OS kernel process table handles.
- **`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`:** Guaranteed teardown semantics. Closing the Job Object handle automatically terminates all active child, grandchild, and descendant processes.

### 3.2 Nesting Compatibility & Breakaway Denial
- Modern Windows 10/11 and Windows Server 2016+ support nested Job Objects natively.
- To prevent adversarial code from escaping the job via `CreateProcessW(..., CREATE_BREAKAWAY_FROM_JOB)`, Sarthi omits `JOB_OBJECT_LIMIT_BREAKAWAY_OK` and `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`. Any child attempt to break away fails with `ERROR_ACCESS_DENIED`.

## 4. Race-Free Process Creation & Boundary Lifecycle

The complete process spawn lifecycle is engineered to guarantee zero window of uncontained execution:

```
+-----------------------------------------------------------------------------------+
| 1. userenv.CreateAppContainerProfileW(unique_profile_name)                        |
|    -> Generates ephemeral LowBox Security Descriptor & AppContainer SID           |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 2. Additive DACL Scoping (icacls /grant:r AppContainerSID:...)                    |
|    -> Grants workspace (OI)(CI)(F) and Python runtime (OI)(CI)RX                  |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 3. ntdll.NtCreateLowBoxToken(primary_token, AppContainerSID, CapabilityCount=0)   |
|    -> Derives genuine restricted AppContainer primary token                       |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 4. Create Win32 Job Object & SetExtendedLimitInformation                          |
|    -> JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | ActiveProcessLimit | JobMemoryLimit   |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 5. advapi32.CreateProcessAsUserW(LowBoxToken, CREATE_SUSPENDED, PROC_THREAD_ATTR) |
|    -> Handle containment: ONLY stdout/stderr pipe write handles are inheritable   |
|    -> Environment: Stripped, sanitized Unicode environment block                  |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 6. kernel32.AssignProcessToJobObject(JobHandle, ProcessHandle)                    |
|    -> kernel32.IsProcessInJob(ProcessHandle, JobHandle, &in_job)                  |
|    -> FAIL-CLOSED ASSERTION: If in_job == FALSE, terminate and raise error        |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 7. kernel32.ResumeThread(ThreadHandle)                                            |
|    -> Subprocess begins execution inside AppContainer and inside Job Object       |
+-----------------------------------------------------------------------------------+
                                          |
+-----------------------------------------------------------------------------------+
| 8. Execution, Stream Drain & Teardown                                             |
|    -> Asynchronous stdout/stderr pipe reader threads                              |
|    -> Job Object closure kills process tree; profile deleted via userenv          |
+-----------------------------------------------------------------------------------+
```

## 6. Cross-Platform Parity Matrix

| Capability / Threat | Linux Backend (SEC-01C.3) | Windows Backend (SEC-01C.4) |
|---|---|---|
| **Security Isolation Boundary** | Bubblewrap unprivileged user/mount/pid/ipc/net namespaces (`bwrap`) | Windows AppContainer LowBox Token (`NtCreateLowBoxToken`) |
| **Filesystem Isolation** | Pivot root + explicit read-only bind mounts (`--ro-bind /usr /usr`) | Additive DACL scoping on ephemeral workspace (`icacls /grant:r`) |
| **Resource Quotas** | Linux cgroup v2 (`memory.max`, `pids.max`) | Win32 Job Objects (`JobMemoryLimit`, `ActiveProcessLimit`) |
| **Network Restriction** | Network namespace unsharing (`--unshare-net`) | WFP zero-capability enforcement (`CapabilityCount = 0`) |
| **Process Teardown** | PID namespace exit / cgroup subtree freeze & kill | Job Object `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` |
| **Race-Free Containment** | Pre-exec pipe synchronization barrier before bwrap launch | Process suspended launch + Job Object binding before `ResumeThread` |
